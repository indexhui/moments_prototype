# 展覽版多語系翻譯原則

最後更新：2026-08-28

本文件定義展覽版繁體中文、日文與英文的翻譯原則、固定譯名、角色口吻、介面用語與驗收標準。適用範圍包含開始畫面、主線對話、地點轉場、路線玩法、拍照玩法、辦公小遊戲、日記、系統完成畫面，以及玩家可見的無障礙文字。

繁體中文編劇文本是目前的內容基準。翻譯可以為了自然度調整語序、斷句與慣用語，但不可自行改變事件因果、角色關係、謎題答案、玩家操作或情緒節點。若文件與已核准的最新編劇腳本不同，以最新核准腳本為準；若腳本與程式目前行為不同，需先確認差異，不可由譯者自行選擇版本。

## 適用語系與代碼

| 語系 | 顯示名稱 | 建議程式代碼 | HTML `lang` |
| --- | --- | --- | --- |
| 繁體中文 | 繁體中文 | `zh-Hant` | `zh-Hant` |
| 日本語 | 日本語 | `ja` | `ja` |
| English | English | `en` | `en` |

- 不再以模糊的 `zh` 代表繁體中文。
- 語系代碼、phase ID、step ID、speaker ID 與資源 ID 不因翻譯而改變。
- 展覽共用裝置不應永久沿用上一位玩家的語系；回到標題或閒置逾時後，依現場設定恢復預設語言。

## 核心原則

1. 以自然在地化為目標，不做逐字直譯。
2. 保留每句台詞原本的情緒、資訊量與演出功能。
3. 除非經編劇與流程實作者確認，不新增或刪除需要玩家點擊的對話節點。
4. 長句優先精簡或在同一文字內換行，不直接拆成新的 step。
5. 舞台指示不翻成玩家台詞。黑色括號描述仍由背景、角色、動畫、音效或轉場呈現。
6. 角色內心話要翻成自然的第一人稱心聲，不保留編劇稿用的括號。
7. UI 用語保持短、清楚、可操作；敘事台詞則保留角色個性。
8. 同一專有名詞只能有一個核准譯名。若需要口語變體，必須在本文件註明使用情境。
9. 圖片內文字、Logo、無障礙文字與音效相關字幕都屬於多語系範圍，不能只翻畫面上的 React 文字。

### 「小日獸」命名說明

- 日文建議使用 `ヒビモン`，可聯想到「日々」與可收集生物名稱，也與專案既有 `Hibimon` 內部命名相容。
- 英文建議使用 `Momentling`，由 `moment` 與表示小型生物的 `-ling` 組成，能和 `Ditto MOMENTS` 的品牌語意連結。
- 不建議使用 `Sunbeast`。它容易把「日」誤解為太陽，且 `beast` 的攻擊性高於目前作品氣質。
- 不建議使用 `Daily Beast` 或 `Little Day Monster`，這些名稱像功能描述或直譯，不像角色 IP。
- 若品牌策略要求全球統一單一專名，可把英文改為 `Hibimon`；一旦決定，必須同時更新 UI、台詞、圖鑑、宣傳與字幕。

### 不可翻譯或不可改名項目

以下內容保持原始技術值，只翻譯其玩家可見標籤：

- `ExhibitionPhase` 與 phase ID，例如 `metro-dog`、`frog-dessert`。
- scene step ID，例如 `EX-DEPART-00`、`line-5`、`diary-photo-slide`。
- `speakerId`、`spriteId`、表情 frame index、motion ID、audio cue ID。
- URL 參數名稱，例如 `preview`、`sceneStep`、`lang`。
- 程式屬性名稱、事件名稱、儲存 key 與素材路徑。
- 內部類型名稱 `Sunbeast`、`Hibimon` 不代表已核准的玩家顯示譯名。

## 角色口吻

### 小麥／ムギ／Mugi

- 是玩家代表角色；敘事不可把玩家正在做的選擇改成旁觀小麥行動的第三人稱說明。
- 語氣自然、親切，緊張時會自言自語，遇到荒謬情況會輕微吐槽。
- 日文使用自然的「私」「～かな」「～しなきゃ」，避免過度大小姐或動畫腔。
- 英文使用簡短口語與 contractions，例如 `I’m`、`can’t`、`that’s`，避免正式書面語。

### 小白／シロ／Shiro

- 目前主要透過回憶與日記呈現。
- 日記使用第一人稱，語氣隨性、真誠，帶有少根筋與自嘲感。
- 不把她寫成刻意搞笑或不負責任；笑點來自她對日常事件的自然反應。

### 小貝狗／ベイゴ／Beigo

- 語氣幼小、積極、情緒外放，但提供關鍵規則時仍要清楚。
- 中文招牌叫聲「嗷嗷」建議依情緒處理：
  - 日文興奮：`あおーん！`、`あおん、あおん！`
  - 日文低落：`あおーん……`
  - 英文興奮：`Awoo!`、`Awoo, awoo!`
  - 英文低落：`Awooo...`
- 不固定翻成 `Woof!`，因為目前「嗷」比較接近拉長的嚎叫，也是角色辨識的一部分。

### 同事

- 與小麥熟悉，日文可使用輕鬆同事口吻，不需要句句敬語。
- 英文維持友善、生活化，不添加職場階級或上下屬關係。

### 店員

- 日文採服務業禮貌語；口誤時可出現結巴與立即修正。
- 英文先保持店員用語禮貌，再以破折號或結巴表現慌張。

### 旁白

- 用字簡潔，只陳述玩家需要知道、而且沒有由畫面充分呈現的資訊。
- 不把原編劇表格中的黑色舞台指示全部轉成旁白。
- 日文避免過度文學化；英文優先使用清楚的過去式敘事。

## 日文翻譯規則

- UI 優先使用日本遊戲常見的短語，例如 `はじめる`、`つづける`、`タイトルへ`。
- 對白使用現代自然口語，不逐字保留中文語序。
- 中文的「～」「⋯⋯」「！」不可機械式全部照搬；依角色情緒調整為 `〜`、`……`、`！`。
- 同一個對話框內避免連續使用多組刪節號。
- 專有名詞首次出現可使用括號或引號強調，例如 `「ヒビモン」`；後續不必句句加引號。
- 「公司」若指實際上班場所，使用 `オフィス`；只有在談論企業組織時才使用 `会社`。
- 「捷運」一般使用 `地下鉄`；若畫面或場域明確指台灣品牌路網，可使用 `MRT`。
- 「甜點店」場景標籤用 `スイーツ店`，角色口語談買蛋糕可用 `ケーキ屋`。

## 英文翻譯規則

- 採自然、溫暖的遊戲英文，不保留中文主題省略造成的生硬句型。
- 使用 contractions，除非角色刻意強調，例如 `I can’t`、`you’re`、`that’s`。
- 獨立按鈕、選單項目與短標題採 Title Case，例如 `Select Chapter`、`Continue`、`Take Photo`；完整提示句採 sentence case。
- 同一流程固定使用 `diary`，不在 `diary`、`journal`、`notebook` 之間任意切換。
- 場景中的「公司」使用 `office`，不用 `company`。
- 「捷運」使用 `metro`，除非句子明確指列車本身，此時可用 `train`。
- 台灣貨幣在玩家可見英文中寫為 `NT$108`，不單獨寫 `108 yuan`。
- 不將角色名翻譯成字面意思，也不加未經確認的姓氏、敬稱或暱稱。
- Beigo 與其他性別未核准的角色，避免自行指定英文代名詞；可重複角色名或改寫句子。

## 對話與節奏

- 翻譯單位以穩定 line ID／step ID 為主，不以陣列索引或畫面截圖作為唯一識別。
- 每句必須附上 speaker、場景、是否內心話、前後句與演出提示，避免脫離情境翻譯。
- 英文通常比中文長，應先刪除重複主詞或贅詞，再考慮換行。
- 日文與英文可在同一 step 中加入人工換行，但不可讓換行切斷專有名詞、否定詞或謎題答案。
- 若翻譯後必須增加新的點擊節點，需新增穩定 step ID，並同步更新直接跳轉、回顧與 Unity 資料；這不是譯者可單獨決定的文案調整。
- 對話逐字顯示速度需以各語系實測。英文不可單純按字母數沿用中文速度，否則同一句會明顯變慢。

建議視覺目標，而非未經實測的硬限制：

- 日文每個視覺行約 16–22 個全形字元，盡量不超過 3 行。
- 英文每個視覺行約 30–42 個字元，盡量不超過 3 行。
- 超出時先進行 copy edit；仍無法容納才調整字級、容器或演出節點。

## 對話語意配色

對話框與回顧紀錄使用同一套語意配色。配色是辨識輔助，不取代角色名或文字本身；所有內容即使在黑白、低彩度或色覺差異條件下仍須可讀。

### 正文重要詞分類

| 分類 | 色票 | 範例 |
| --- | --- | --- |
| 小日獸／角色專名 | 角色固定色或 `#FFE08A` | 黃金獵犬、青蛙、ヒビモン、Momentling |
| 日記 | `#FFC7AA` | 交換日記、日記片段、diary fragment |
| 照片／相機 | `#9FE4E0` | 照片、カメラ、photo |
| 線索／地圖／紙膠帶 | `#C6E99B` | 線索、ヒント、masking tape |
| 關鍵地點 | `#C7C9FF` | 捷運、便利商店、スイーツ店、street |

- 只標示專有名詞、謎題答案與玩家需要記住的遊戲元素，不替一般動詞、情緒詞或整句上色。
- 採最長詞優先匹配，例如「交換日記」不可再拆成「日記」重複套色。
- 同一個對話框最多標示兩個重點；同一分類只標第一次，後續重複詞維持正文白色。
- 若前面已標示日記、照片、線索、地點或小日獸等遊戲元素，後續才出現的角色名不再加色，避免一句話出現過多色塊。
- 例：「日記……是指我早上帶出門的小白日記本嗎？」只標前面的「日記」，後面的「小白日記本」維持白字。
- 逐字顯示期間只替已完整出現的詞套色；打字動畫完成後的內容與回顧紀錄必須得到相同結果。
- 日、英文使用各自核准詞彙匹配，不以中文原文位置硬套顏色。

## 日記與拼圖翻譯

日記是展覽版多語系的獨立排版項目，不可只替換正文字串。

- 每個語系分別保存核准斷行，不依瀏覽器自動換行作為最終結果。
- 日文可以按字素拆分，但仍需檢查標點禁則、行首行尾與直覺閱讀順序。
- 英文不可用 `Array.from(text)` 逐字母生成拼圖。應按單字、片語或經設計的 fragment token 切分。
- 中文謎題中的底線數量不代表英文字母數。答案應是語意 slot，例如 `street`、`convenienceStore`、`dessertShop`。
- 殘缺文字、拼圖完成文字、照片後揭露文字與完整日記必須引用同一份語意內容，不能各自獨立翻譯。
- 上半段拼圖不得提前露出下半段內容；照片揭露頁也不可重播已讀過的上半段。
- 黃金獵犬與青蛙日記都要為三個語系分別驗證字級、行距、紙張留白、碎片格與動畫遮罩。
- 日記標題與日期可以依語言改排，但不可改變事件日期或篇章順序。

## 在地化與文化資訊

- 笑點以「在該語言中產生相同效果」為原則，不要求詞面一致。
- 台灣場景與飲食不需要全面改成日本或英語文化中的對應物；應保留作品所在地特色，再用自然譯名說明。
- 金額、單位、日期與時間格式需明確，不能讓海外玩家誤判幣別。
- 不自行新增日本敬稱或英文暱稱來補充原文沒有的角色關係。
- 不把「涼麵」改成 soba、ramen 或 Korean cold noodles。

便利商店口誤範例：

繁體中文：

> 店員：這樣是108元，涼麵需要微波嗎？
> 小麥：欸……可是涼麵微波了，就不涼了餒……
> 店員：我、我是說，涼麵需要餐具嗎？

日本語：

> 店員：108台湾ドルです。冷やし麺は温めますか？
> ムギ：えっ……温めたら、冷やし麺じゃなくなりません……？
> 店員：し、失礼しました！　お箸はお付けしますか？

English:

> Clerk: That’ll be NT$108. Would you like your cold noodles heated up?
> Mugi: Heated? Then they wouldn’t be cold noodles anymore...
> Clerk: S-sorry! I meant—would you like utensils?

## 翻譯示例

### 開場旁白

繁體中文：

> 身為上班族的小麥，最近遇到了一個煩惱⋯⋯

日本語：

> 会社員のムギは最近、あることで悩んでいた……。

English:

> Lately, Mugi had a problem weighing on her...

### 小日獸首次說明

繁體中文：

> 那不是黃金獵犬！是一隻「小日獸」！

日本語：

> 違うよ！　ゴールデンレトリバーじゃない！「ヒビモン」だよ！

English:

> That’s no golden retriever! It’s a Momentling!

### 黃金獵犬日記

日本語：

> 寝坊して、地下鉄に駆け込んだ。
> なんとか乗れたと思ったら、みんなが私を見ている。
> 下を見ると、ギターケースがドアに挟まっていた。
> 次の駅ですぐ助け出せて、思わず自分でも笑ってしまった。

English:

> I overslept and barely made it onto the metro.
> Then I noticed everyone staring at me.
> When I looked down, my guitar case was caught in the doors.
> Luckily, I freed it at the next stop. I couldn’t help laughing at myself.

## 圖片、Logo 與無障礙文字

- 標題畫面使用現有 `zh-Hant`、`ja`、`en` Logo，不以 CSS 文字重畫品牌 Logo。
- 其他轉場若仍使用繁中 Logo，必須依 locale 切換相同品牌組合。
- `GREAT!`、`MISS` 等圖片文字若決定作為語言中立視覺，可三語共用；仍需在素材清單中標示已確認。
- 場景招牌、文件卡、漫畫格與背景中的烤字需逐張稽核。純裝飾且不影響理解的環境文字可保留，但情節關鍵文字必須翻譯或改成程式疊字。
- `alt`、`aria-label`、dialog title、range input label 與鍵盤操作提示都必須跟著 locale 改變。
- 純裝飾圖片保持空 `alt`，不因多語系加入多餘描述。

## 字型與排版

- 展場執行環境不可依賴工作電腦剛好安裝的字型。
- 繁中、日文與英文需有明確 font stack 或隨專案載入的授權字型。
- 日文字型需完整支援假名、日文標點與常用漢字；不可只指定 `Noto Sans TC`。
- 英文需檢查長單字、撇號、破折號、百分比與按鈕大小寫。
- 所有語系以手機舞台 `393 × 852` 為主要視覺驗收尺寸。

## 翻譯資料交付格式

每個翻譯單位至少包含：

| 欄位 | 說明 |
| --- | --- |
| `id` | 穩定 line／step／UI key |
| `speakerId` | 穩定角色 ID；非顯示名稱 |
| `context` | phase、畫面、是否內心話、前後事件 |
| `zh-Hant` | 核准繁中基準文案 |
| `ja` | 日文翻譯 |
| `en` | 英文翻譯 |
| `notes` | 謎題答案、笑點、舞台指示、字數限制等 |
| `status` | `draft`、`reviewed`、`approved` |

- 不以檔案行號作為永久翻譯 key。
- 變數與插值使用具名 placeholder，例如 `{count}`、`{location}`，不可讓譯者自行猜測 `%s` 的意義。
- 同一 key 的三語必須同時存在；缺少核准翻譯時，在開發版明確顯示 missing key，不可悄悄混入繁中 fallback 後送展。

## 建議工作流程

1. 凍結角色名、作品名與「小日獸」全球命名。
2. 依穩定 ID 匯出正常展覽主線的繁中基準文案與情境欄位。
3. 先翻 UI、角色名與場景標籤，確認整體語氣。
4. 翻主線對話，進行角色口吻編修。
5. 將日記交由獨立批次翻譯與逐頁排版，不和一般 UI 字串混在一起處理。
6. 回填遊戲後，以每個 phase／sceneStep 深連結進行三語畫面驗收。
7. 由日文與英文母語編修者進行 linguistic QA。
8. 完成現場裝置的開始、切換語言、返回標題、重新開始與閒置重設測試。

## 驗收清單

- 三語都能從標題畫面開始完整遊玩正常展覽主線。
- 遊戲中切換語言不重設目前 phase、step、日記與拍照狀態。
- 章節接續與 `preview`／`sceneStep` 深連結能攜帶正確 locale。
- speaker 顯示名稱、對白、內心話、地點、按鈕、提示、回顧與完成卡全部切換。
- 日文沒有殘留玩家可見繁中；英文沒有殘留未核准的漢字文案。
- 所有專有名詞符合「建議固定譯名」。
- 便利商店口誤、Beigo 叫聲與其他笑點在兩種譯文中仍成立。
- 黃金獵犬與青蛙日記的殘篇、拼圖、揭露與完整頁內容一致。
- 英文拼圖不是逐字母拆分，日文拼圖沒有錯誤行首／行尾標點。
- `393 × 852` 下沒有截字、溢出、按鈕壓縮、過度縮字或遮住角色。
- 對話逐字速度、音效觸發與動畫等待在三語下都合理。
- `html lang`、局部 `lang`、alt 與 aria-label 都與目前語系一致。
- Logo 與其他含字圖片已完成三語素材稽核。
- 展場重新開始或閒置重設後，不會讓下一位玩家困在上一位選擇的語言。

## 待品牌／編劇確認

- 英文「小日獸」最終採 `Momentling`，或全球統一採 `Hibimon`。
- `Beigo` 是否為小貝狗的正式全球拼法。
- Beigo 與各小日獸的英文代名詞設定。
- 日文場景中「捷運」統一使用 `地下鉄`，或為台灣場域保留 `MRT`。
- 繁中、日文與英文正式 Logo 在所有轉場與宣傳物的使用規則。
- 圖片內 `GREAT!`、`MISS` 是否正式核准為三語共用語言中立素材。
